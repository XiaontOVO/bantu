# 伴途｜作品说明与演示

> 更新：2026-10-10。主线为用户需求、连续任务和可观察结果。新增跨界面 Agent 导演剪辑版；研究、持续内测、实际功能与待验证收益分别说明，精确工程证据统一见[体验核查](产品体验全盘核查.md)。

## 作品简介：可直接用于提交

**作品名称：伴途——手机上的城市漫游伴侣。**

伴途面向自主安排半日到一日城市漫游的人，聚焦散步、建筑探访和看展。途中想休息、改变停留或换个地点，需要重新衔接后面的安排；到了地点，想知道眼前值得看什么；结束之后，也希望留住自己的经历。伴途把这些任务接在同一份旅程里：一句话委托Agent调整后续安排，保留已经发生的进度，改完直接继续；到场后点选画中元素看讲解，在不遮断页面的小窗随时提问；完成后打开对应私人回顾，补写本人感受，分享范围由本人决定。当前以上海城市漫游为原型验证范围。

**一句话价值：专心逛，随时问，随时改，走完留下自己的旅行。**

**品牌表达：让每一步，都跟得上真实旅途。**

## 解决谁在什么时候的什么问题

首批对象按行为定义：已有几个想去的地点，自主安排城市短游，愿意根据当天状态调整，由一人维护安排；可以独自或与少量亲友同行。年轻旅行者是当前视觉与交互的首批设计对象，不是已证明的唯一用户，也不是公开研究得出的中国青年画像。

主任务发生在旅途中：计划执行了一部分，新的情况改变了后续需求。用户除了决定“要不要改”，还要查需要的信息、核对余下时段并把修改接回原行程。伴途希望把这段整理工作交给可执行的Agent，让用户看到实际变化并继续。参观时的提问与旅后的私人记录是两项支撑任务，它们沿用当前地点、计划与进度，避免成为互不相干的聊天、插画和社区功能。

下列负担是任务分析，不是已测得的发生率或耗时；演示中的人物、疲倦情境与日期是演示故事，不冒充独立访谈。

| 用户需要 | 需要处理的负担 | 产品里的实际动作 | 用户能观察到的结果 | 证据及待验证项 |
| --- | --- | --- | --- | --- |
| 途中休息、少停一会或换下一站 | 核对能调整的后续时段、交通、原来要保留的安排 | 小窗说出变化；Agent读取当前计划、必要时查询信息并保存 | 原计划仍在，已经发生的进度保留，新的后续安排能继续执行 | 本次实录真实休息：同计划、已完成站与事件不变，后两站各顺延30分钟；真实用户理解、耗时与现场成功率未测 |
| 到地点知道值得看什么，随手追问 | 把眼前元素、资料与自己的问题联系起来，同时还能操作页面 | 点画中元素、阅读/听讲解；附带当前地点的可移动小窗；查看地图与场地/楼层 | 元素对应内容，提问后仍能继续参观；图纸放大返回同一层 | 横屏点红砖、BGM、小窗、2F返回已验证；场馆资料与真人听感另验 |

## 需求依据：旅中行为研究与持续内测

### 直接相关的原始研究

[Micol Mieli：Planned serendipity: exploring tourists’ on-site information behaviour](https://rucforsk.ruc.dk/ws/portalfiles/portal/100678975/Planned_serendipity_exploring_tourists_on-site_information_behaviour.pdf)，2023-04-07在线发表，刊于2024年《Current Issues in Tourism》27(6)，988–1002，DOI 10.1080/13683500.2023.2197198。大学仓储提供出版原版。

研究于2019-05至2020-03采集15次访谈和14组旅中ESM，共93份短问卷。志愿参与者出生于1980–2000年，以城市旅游与自主安排行程为主；这是质性研究，不能据此统计外推中国旅者或2026年的青年需求。

研究观察到，天气、饥饿和疲劳会改变计划，旅中检索也需要在多个网页间反复处理信息。因此，“到现场以后仍要决策”是与伴途直接相关的设计依据。把调整落实到原行程、接着执行，是本产品提出的回应，不是该论文验证过的解决方案或收益。

### 行业背景与政策另行看

[中国旅游研究院与求是杂志社经济编辑部：2026年春节旅游市场调查](https://www.ctaweb.org.cn/gongzuodongtai/10440.html)，2026-04-02发布。报告中深度体验、慢游与短停留的矛盾提供行业启发；相关观察主要讨论传统供给。跨平台认证、系统切换涉及预订与服务协同，不能偷换成自主漫游者反复切换规划、地图、讲解App的统计。

[文化和旅游部等五部门：智慧旅游创新发展行动计划](https://zwgk.mct.gov.cn/zfxxgkml/zykf/202405/t20240513_952825.html)，2024-05-13发布、2024-05-06落款。手机可用、旅游助手、隐私与实际效用是设计取舍的政策背景；不是用户需求调查、官方认可或产品背书。

旅游人数、旅游意愿与场馆出游比例只说明场景可能存在，不能证明用户需要伴途，也不能代替以上具体任务论证。本次不再将此类市场规模数字放在问题页中心。

### 持续内测提出的明确要求

| 用户原话或连续片段 | 对设计的直接要求 |
| --- | --- |
| “谁会拿着电脑去景点游览？” | 手机是现场主界面，桌面用于整理与演示 |
| “想要休息都不知道怎么安排。” | 回复需要落实到安排，不能只给建议或敷衍 |
| “打开之后不影响其他功能。” | 小窗可移动、可收起，页面继续可操作 |
| “我希望agent能真正陪伴用户参观，在合适地时候介绍相关景点。” | 知道当前地点与所选元素，再给相关内容 |
| “帖子应该能设置为private 不公开。” | 私人保存与公开分享分开 |

这些来自本产品开发中的持续内测与设计反馈，不是独立问卷、多人访谈或统计样本。已解决的反馈报告按要求清理，验收记录维护在[体验核查](产品体验全盘核查.md)。没有独立用户收益、节省时间、留存或付费数据。

## 与通用行程规划的差异应怎样证明

伴途把原安排、实际进度、当前地点和私人回顾放进连续任务：**Agent给出的建议实际写入产品，再回到原旅程继续。** 评审可直接核对同一计划、已经发生的事实和下一步是否可用；到场后的内容与私人回顾沿着这次旅程展开。

| 需要让评审看到的差异 | 具体证明 |
| --- | --- |
| 改的是正在使用的旅程 | 同一planId，修改后首页和行程显示实际新安排 |
| 已经发生的事情不会被新计划覆盖 | 修改前后出发/到达事实保持，完成的站点仍可回看 |
| 模型真的操作软件 | 展示实际工具结果与保存状态，再继续使用；信息不足追问，失败不冒充成功 |
| 陪伴留在当前参观中 | 场景点选与相关提问，小窗开着也能操作原页 |
| 回顾对应本人经历 | 完成后打开对应记录，补写本人原话，公开需本人选择 |

这不是竞品普查，不断言所有通用规划产品都只生成清单，也不宣称行业首创或唯一。模型、地图供应商与工具调用本身不构成独占优势；少量地点资料、任务连续性与实际操作的组合是当前重点。能否让目标用户感知价值，仍需要任务测试。

本次主演示中的休息任务已保存：第一站完成后委托休息半小时，真实模型调用 `plans.rest`，同一计划标识保持，已完成站的整个对象和执行事件一致，后两站的开始与结束各顺延30分钟，没有新方案。验证日志包含五项对应断言；该轮后续在私人回顾补写阶段超时，不能据休息成功称整条录制全部成功。未保留完整休息前后对象，介绍页只展示已验证结果示意，不编造确切时刻或计划编号。

另有独立APK例子：在武康大楼游览中，要求末站西岸美术馆由45分钟改为30分钟，其余开始时间及已有进度保留，不创建新方案。真实APK模型任务将同一计划revision3更新到4，开始14:10/15:07/16:04不变，末站结束16:49改为16:34，原出发与到达记录保留。随后可继续三站并补写同一私人回顾。这证明该任务可执行；不证明任意表达、网络或现场情况都成功。

| --- | --- | --- |
| 00:39 行程安排 | 说出这一天想去哪里、怎样安排 | 真实模型建立具体日计划，页面显示可执行的地点与时段 |
| 01:32 地点详情 | “把这个地点加入今天的计划”，放在后面、停留45分钟，保留原两站 | 当前西岸详情进入上下文；`plans.edit` 追加同计划到访节点，实际道路校正后续时刻；收起小窗继续原详情页 |
| 02:24 地图与路线；03:16 保存结果 | 去地图终点改用驾车，保留其他地点与时长 | `plans.route_segment` 保存公安博物馆→西岸的驾车路段；道路查询16分钟、4.15公里，第三站实际卡显示驾车约21分钟（含5分钟缓冲）、15:27–16:12／45分钟 |

| 04:09 首页随行 | 第一站完成后休息半小时 | `plans.rest` 在原计划顺延后两站各30分钟，已完成站和事实保留；查看楼层后从原旅程继续 |
| 05:34 私人回顾 | 把本人的感受补进当前记录 | 独立回顾示例用 `memories.edit` 保存本人原话，放大已保存文本；06:13之后由本人手动私密发布，权限核对不冒充 Agent 发布 |

地点与地图录制在独立内存服务中预置当天两站待执行计划，没有实际到访记录。当前地点和地图端点均进入服务端复核的界面上下文；新增与交通修改由真实官方模型调用工具完成，之后检查同一计划的真实保存对象。地图的手动路线查询选择器独立存在，影片没有声称其步行下拉自动切成驾车。第三站结果补镜只恢复原先实际保存的快照并滚动，0次新模型调用或计划修改。

本轮保留两项实际局限：地点第一次写入漏传时长，被工具拒绝后模型补齐并保存；地图回复曾将15:27–16:12误写为15:27–16:22，影片提示说明不一致，再展示正确保存字段。没有为了画面重新生成一个全程无错误的模型结果；这些回复问题尚未修复。

静态等待经过剪短，字幕标明请求实际耗时：日计划创建28.10秒、地点追加35.13秒、地图交通修改23.86秒、场景问答13.98秒。片长和剪辑后的等待不能当成响应速度。详细版主线回顾曾超时，导演版的成功补写与后续分享明确标注为独立示例；元素音乐采用同元素独立实录采样，设备TTS未录入。定位和时钟仍为演示输入，道路是真实查询，不能作为现场手机导航验收。精确录制与媒体证据见[体验核查](产品体验全盘核查.md)。

## 现阶段的证据与边界

当前原型可本地运行，SQLite持久化，有可安装Android客户端与真实模型工具链。原生验证分别覆盖同计划调整/进度保留/回顾补写、邀请码与HTTP认证、账号与私密内容、会话、横屏/BGM、TTS事件、图纸显示返回、冷启动；平台夹具验证权限和文件上传。完整证据以[体验核查](产品体验全盘核查.md)为准，不逐页堆测试数量。

服务端保留模型密钥；官方Agent或账号自接服务由服务器执行。APK需可达后端，不包含数据库、模型密钥或完整离线业务。当前正式服务仅本机运行，安装App不会自动开放网络。

场景是原创艺术画面，不能当实景、真实相邻关系或导航。场地/楼层资料性质与来源不同，数量不是准确率；普通GPS不识别室内楼层。实际出发、到达、完成由用户报告，不由定位、预测或时钟自动产生。自动到场提示需主动开启且仅前台条件合格时生效。

本次主线补写的服务超时、用计划名关联回顾标题的歧义，以及补录中的模型参数遗漏和回复时间不一致仍待改进。现场GPS、真实弱网、中文输入法、音频路由与人耳听感、设施资料仍待实机/实地验收，用户已允许保留待验项。没有票务支付、多人实时协作、专业逐转导航、室内实时定位或完整离线能力。工程验证证明覆盖任务的行为，不证明市场认可或用户收益。

## 下一步怎样验证价值

拟邀请6–8名目标用户做探索性任务测试，尚未开展。任务使用“已有计划、已完成一站、想休息且后面有保留安排”的同一场景，观察普通清单编辑与伴途委托入口：是否重填已知信息、是否看懂变更、能否继续、是否误改事实；再观察一次地点提问和私人记录。记录时间与阻塞原因，不将小样本写成统计领先。
